\section{Datasets}
\label{sec:datasets}

The empirical evaluation uses two publicly available datasets published on
IEEE DataPort by the NES@FIT group at the Faculty of Information Technology,
Brno University of Technology.

The first dataset, \emph{Modbus Dataset for ICS Anomaly Detection}
\autocite{RysavyMatousek2021Modbus}, captures Modbus traffic from a
controlled industrial testbed. The exposé originally planned to source the
function-code-violation and replay-attack event types from this dataset. In
the implemented pipeline this has not yet happened: both event types are
currently derived as proxies from the second (smart-grid) dataset described
below, and the Modbus dataset itself is not yet consumed by any pipeline
stage. Section~\ref{sec:event-type-distribution} reports the resulting
counts, and this scope gap is carried forward as a stated limitation and
future-work item in Chapter~\ref{ch:discussion}.

The second dataset, \emph{ICS Dataset for Smart Grid Anomaly Detection}
\autocite{MatousekRysavyGrofcik2022SmartGrid}, captures IEC-104 traffic from
a smart-grid testbed. The pipeline currently uses the eon-iec subset of this
dataset; the working file is \texttt{data/raw/sample\_003.csv} with 20\,000
atomic IEC-104 rows.

\section{Proxy Event-Type Distribution}
\label{sec:event-type-distribution}

Under the proxy classifier (Section~\ref{subsec:proxy-event-types}) the
20\,000 IEC-104 bounds decompose into four observed event types:

\begin{center}
\begin{tabular}{lr}
  \toprule
  Proxy event type & Count \\
  \midrule
  normal\_modbus\_polling & 16\,205 \\
  topology\_change & 3\,683 \\
  network\_scan & 68 \\
  function\_code\_violation & 44 \\
  replay\_attack & 0 (absent from sample) \\
  \bottomrule
\end{tabular}
\end{center}

The fifth canonical event type (replay attack) is absent from the current
sample. The evaluation therefore covers four of the five canonical event
types under the proxy regime. Both \texttt{function\_code\_violation} and
\texttt{replay\_attack} are named in the exposé as Modbus-sourced event
types (Section~\ref{sec:datasets}); in the current pipeline
\texttt{function\_code\_violation} is instead observed as a proxy label on
the smart-grid dataset (44 of 20\,000 bounds) and \texttt{replay\_attack}
does not occur at all. A chi-square test of independence confirms that the
distribution of ReasonGuard violation verdicts is significantly associated
with proxy event type ($\chi^2=39.09$, $df=12$, $p<0.001$; full results in
\texttt{outputs/chi\_square\_tests.md}), i.e.\ the event-type signal is not
noise even under the proxy schema. Sourcing both event types directly from
the Modbus dataset remains future work (Chapter~\ref{ch:discussion}).

\section{Language Models}
\label{sec:models}

\subsection{Local Models}
The pipeline runs three local models through Ollama 0.23.3 with 4-bit
quantisation on a CPU-only inference path:

\begin{itemize}
  \item \texttt{llama3.1:8b-instruct-q4\_0} ($\approx$ 4.7~GB on disk).
  \item \texttt{mistral:7b-instruct-v0.3-q4\_0} ($\approx$ 4.1~GB on disk).
  \item \texttt{phi3:mini} ($\approx$ 2.2~GB on disk).
\end{itemize}

Each call uses the same generation parameters: temperature 0.1, top-p 0.9.
Latency on the reference hardware is approximately 11--14 seconds per
prompt for the 7B and 8B models, and approximately 11~seconds for
\texttt{phi3:mini}.

\subsection{Cloud Models}
\label{subsec:cloud-models}

The cloud-model batch uses \texttt{gpt-4o-mini} (OpenAI) and
\texttt{gemini-2.5-flash-lite} (Google). The original design specified
\texttt{gemini-1.5-flash}; that model was retired by Google before the
cloud batch was run, so the pipeline configuration
(\texttt{src/cloud\_llm\_runner.py}) was updated to the current
equivalent-tier Flash-Lite model, which is available on Google's free tier.
The runner is implemented as a thin \texttt{urllib} client and gracefully
skips a provider when its API key environment variable is unset.

\section{Prompt Design}
\label{sec:prompts}

Every prompt comprises a fixed analyst system prompt and a user prompt that
embeds the JSON formal bound together with the explicit lists of allowed,
required, and forbidden claims. The user prompt is intentionally verbose so
that any deviation in the LLM output is a deliberate model failure rather
than a prompt-engineering shortfall. Three prompt variants will be compared
in a 20-sample pilot at the start of the W11 evaluation block; the
production variant is the one used to produce all responses reported in
Chapter~\ref{ch:results}.

\section{Stratified Sampling}
\label{sec:stratified-sampling}

To compare model behaviour across event types, prompt selection uses
stratified sampling: \texttt{src/prompt\_builder.py} samples a fixed number
of bounds per proxy event type (controlled by the
\texttt{REASONGUARD\_PER\_EVENT\_TYPE} environment variable, default 20).
The sampler is seeded by \texttt{RANDOM\_SEED} so the selection is
reproducible. The current production run uses 25 bounds per event type,
yielding 100 prompts in total across the four observed event types.

\section{Evaluation Protocol}
\label{sec:protocol}

The evaluation has three populations.

\paragraph{Synthetic regression set.}
For every selected bound the generator produces a small set of canonical
responses, one per V class plus one clean response. This set is the source
of truth for the V1--V5 detector unit tests. It is not used on its own to
draw conclusions about real model behaviour, but a subset is included in the
manual annotation set (Section~\ref{sec:manual-annotation}) as a controlled
check that every violation class -- including classes that occur rarely in
real model output -- is represented in the human-labelled evaluation.

\paragraph{Local-model batch.}
The three local models each produce one explanation per prompt. The
resulting (model, event\_type) cells are the production data analysed in
Chapter~\ref{ch:results}.

\paragraph{Cloud-model batch.}
The two cloud models each produce one explanation per prompt. The results
are added to the same combined report and the same per-event-type analysis.

The verification step is the same for all three populations: every response
is processed by \texttt{src/reason\_guard\_checker.py}, which produces the
V1--V5 violation set, the severity rating, and (when spaCy is installed) the
per-claim three-state verdicts. The merged report
(\texttt{outputs/reason\_guard\_report.jsonl}) combines all three
populations into 1\,000 verified responses: 500 synthetic regression
responses, 300 local-model responses (3 models $\times$ 100 prompts), and
200 cloud-model responses (2 models $\times$ 100 prompts).

\section{Manual Annotation}
\label{sec:manual-annotation}

The exposé requires manually annotated explanation pairs for the M4
milestone (200 pairs). The batch is generated by
\texttt{src/manual\_annotation.py} and saved to
\texttt{annotation/annotation\_batch.csv}, stratified across the three local
models and the synthetic regression set so that every violation class has
adequate support even where it is rare in real model output. A terminal
helper (\texttt{src/annotate\_cli.py}) presents one response at a time and
saves progress after every row so the batch can be labelled incrementally;
the annotator's judgement is recorded without seeing ReasonGuard's own
verdict, keeping the comparison independent. The completed file is saved as
\texttt{annotation\_results.csv}, and \texttt{src/evaluation\_metrics.py}
then computes per-class precision, recall, F1, accuracy, the confusion
matrix, and Cohen's $\kappa$. A separate blind 50-sample batch, built by
\texttt{src/prepare\_expert\_review\_package.py}, is sent to the VUT Brno
second supervisor for independent assessment at the M5 milestone; Cohen's
$\kappa$ between ReasonGuard and that external judgement is reported
alongside the internal annotation results in Chapter~\ref{ch:results}.

On the completed 200-pair internal batch, ReasonGuard's verdicts achieve an
accuracy of 0.30, a macro-averaged F1 of 0.1871, and a Cohen's $\kappa$ of
0.1602 against the human labels (full per-class precision/recall/F1 and the
confusion matrix are in \texttt{outputs/evaluation\_metrics.md} and are
reproduced in Chapter~\ref{ch:results}). Both figures fall short of the
exposé's target thresholds ($\kappa \geq 0.70$, F1 $\geq 0.80$); the
per-class breakdown attributes most of the gap to the V4 (under-specified
reasoning) detector, whose rule-based implementation over-triggers relative
to the human annotation criterion (precision 0.48, recall 0.92 for V4),
while V1 (fabricated reasoning) shows the opposite pattern (precision 0.90,
recall 0.09). This asymmetry, and its implications for using a rule-based
checker as a sole verification gate, is interpreted in
Chapter~\ref{ch:discussion}.
