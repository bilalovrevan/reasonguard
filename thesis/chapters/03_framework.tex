\chapter{The ReasonGuard Framework}
\label{ch:framework}

\section{Three-Layer Architecture}
\label{sec:architecture}

\textsc{ReasonGuard} operates on a three-layer architecture
(Figure~\ref{fig:architecture} once finalised). The first layer is the \emph{formal
layer}, in which an automaton-based detector emits a verified verdict about a network
event. The second layer is the \emph{AI layer}, in which a large language model
produces a natural-language explanation of that verdict. The third layer is the
\emph{verification layer}---the central contribution of this thesis---which checks
the explanation against a machine-readable bound derived from the formal verdict and
classifies any crossing of that bound into a reasoning violation class.

\section{Formal Bound Schema}
\label{sec:bound-schema}

Each network event is converted into a JSON formal bound that lists the facts
derivable from the formal verdict (\texttt{allowed\_facts}), the claims that the
explanation is permitted to make (\texttt{allowed\_claims}), the claims that the
explanation must make (\texttt{required\_claims}), the claims that the explanation
must not make (\texttt{forbidden\_claims}), and a set of machine-checkable constraints
(\texttt{machine\_constraints}). At the time of writing this thesis the schema is
labelled \texttt{proxy\_until\_official\_automaton\_schema}: the structure is
finalised, but the formal-class field is generated by an internal proxy classifier
pending the integration of the official NES@FIT schema.

\section{Reasoning Violation Taxonomy}
\label{sec:taxonomy}

The taxonomy is the primary theoretical contribution of the thesis. Five violation
classes are defined with respect to the bound:

\begin{description}
  \item[V1 Fabricated reasoning.] The AI asserts facts, causes, or entities that are
    not present in or derivable from the formal output.
  \item[V2 Contradicted reasoning.] The AI explicitly contradicts a fact established by
    the formal output.
  \item[V3 Over-generalised reasoning.] The AI produces a correct category but loses
    formally established specifics, reducing actionability.
  \item[V4 Under-specified reasoning.] The AI omits formally established information
    that is operationally required for correct response.
  \item[V5 Incoherent reasoning.] The AI explanation is internally self-contradictory,
    independent of the formal output.
\end{description}

The formal definitions of each class with respect to the bound are given in
Section~\ref{sec:formal-definitions}, and the detection logic is described in
Section~\ref{sec:detection}.

\section{Verification Mechanism}
\label{sec:detection}

For each AI explanation, \textsc{ReasonGuard} executes a three-step verification
pipeline. First, structured claim extraction uses spaCy NER together with a custom
ICS \texttt{EntityRuler} to identify protocol, direction, ASDU field, network endpoint,
attack category, mitigation, normality, and uncertainty entities. Second, bound
comparison classifies each extracted claim as supported, unsupported, or contradicted
by the bound. Third, violation classification maps the pattern of supported,
unsupported, and contradicted claims to the V1--V5 taxonomy using a rule-based
classifier.

\section{Grounding in Runtime Verification Theory}
\label{sec:grounding}

The verification mechanism is grounded in the runtime-verification framework of
\autocite{LeuckerSchallhart2009RuntimeVerification}. The property being verified is
reasoning faithfulness: the AI explanation must not assert facts inconsistent with
the formally verified bound. The formal automaton output serves as the runtime monitor
specification. This grounding distinguishes \textsc{ReasonGuard} from post-hoc quality
evaluation approaches: it is a runtime verification system, not a quality scoring
system.

\section{Implementation Notes}
\label{sec:implementation-notes}

The implementation is structured around five Python modules:
\texttt{formal\_bound\_builder.py} converts raw rows into bounds,
\texttt{prompt\_builder.py} converts bounds into strict prompts,
\texttt{synthetic\_response\_generator.py} produces adversarial responses for V1--V5
regression testing, \texttt{ollama\_llm\_runner.py} executes real local LLM inference,
and \texttt{reason\_guard\_checker.py} performs the verification step. All runs are
tracked in MLflow.
